## 後續追加格式

### D-18：EC2 Demo 與實際 CI/CD（2026-10-11）

使用者另建 parcel-management EC2，授權 SSH 完成主機環境，並明確要求直接建立 CI/CD 程式，使未來推送 GitHub 可自動部署。此決議增加 Demo 基礎設施與部署工作，不代表第二、三階段業務功能已通過驗收，也不增加商業功能。

實作採 GitHub runner 建置與測試、ECR 不可變映像、S3 部署包、OIDC／SSM 通知 EC2。保留 SSH 的「我的 IP」限制，私鑰不放 GitHub；保留原本 frontend Git 歷史，不擅自刪除或提交。AWS／GitHub 身分與資源啟用仍須取得實際 repository 及 AWS 管理存取；目前不以文件或手動部署冒充 GitHub push 已驗收。

每筆包含日期、使用者確認內容、取代哪一條舊決議、受影響 BR / F / AC / Q，以及實際同步的文件。待確認問題獲回答後保留原問題並標記已解決，連到對應決議。

### D-19：CI/CD 依既有 EC2 精簡（2026-10-11）

使用者要求移除專案目前沒有的設定，明確指出 demo Environment、部署命名與額外 AWS 變數檢查。取代 D-18 的技術安排：移除 ECR、S3、OIDC／SSM 及 CloudFormation；改用現有 SSH 與 Docker Compose，傳送 CI 已測試映像到既有 EC2。不建立 GitHub Environment。保留部署排他鎖、健康檢查、版本回復及資料保存。GitHub SSH secret 與 runner 網路來源尚待啟用，商業規則及功能階段不變。

### D-20：CI/CD 改用 GHCR、前後端分開、自動清理（2026-10-11）

使用者說明期望流程：只處理有變更的前端或後端、先測試與編譯、包成映像、EC2 以 pull 取得映像並啟動、移除舊版避免無限增長。其中「EC2 pull」與 D-19 的 SSH 傳送映像不一致，經詢問後使用者選擇改用 GitHub Container Registry（GHCR）。

取代 D-19 的映像傳送方式：CI 將通過串接檢查的映像 push 至 GHCR，EC2 以 digest pull；SSH 只用來傳送部署包及觸發部署，登入 GHCR 使用 workflow 內建的短效 token，不新增 Secret、主機不保留登入資訊。以前端、後端目錄的 Git tree SHA 作為映像標籤，倉庫已有相同標籤即跳過建置，Compose 只重建映像有變更的容器。部署成功後自動清理，只保留 current 與 previous 兩版的映像及版本目錄，不刪除任何 volume。

D-19 其餘內容維持：不使用 ECR、S3、OIDC／SSM，不建立 GitHub Environment，保留部署排他鎖、健康檢查、版本回復及資料保存。本次不新增前後端單元測試框架，不自動刪除 GHCR 上的舊映像版本。

### D-21：根目錄統一 Git 並移除 frontend 獨立 Git（2026-10-11）

使用者建立 https://github.com/yiiom/parcel-management.git，要求將專案關聯、提交並推送，並明確選擇移除 `frontend/.git`。取代 D-17 中 T-08「匯入 frontend 歷史」的安排：該歷史只有一筆 Create Next App 產生的初始提交，不匯入根目錄歷史；移除前完整備份至 `artifacts/frontend-git-backup.git`（不納入版本管理）。根目錄使用 main 分支，前端、後端、部署程式與文件納入同一個儲存庫。T-08 已解決；商業規則及功能階段不變。

使用者隨後要求首次推送先排除程式碼、只放文件。程式碼仍屬於同一個儲存庫的規劃不變，待使用者指示後再提交與推送。商業規則及功能階段不變；同步文件為 `docs/cicd-deployment.md`、`docs/development-plan.md`、`docs/README.md`。
