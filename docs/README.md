## 發現不一致時

使用者最新明確決議是依據，應先落實到商業邏輯。其他文件與程式均須符合商業邏輯；若發現矛盾，不得直接依文件優先級猜測使用者想法，須先提出差異詢問。

已確認規則與待確認建議分開保存；尚未定案的建議不得作為開發驗收依據。現有草案的 API 欄位或預覽內容也不能自行升格為商業規則。

功能使用 F 編號、規則使用 BR 編號、驗收使用 AC 編號、問題使用 Q 編號，供文件交叉追蹤。第一版功能清單與後續候選功能分開，避免開發範圍自行擴張。
